## 3. 지금까지 한 작업과 유지할 결과

### 지형

원래 stage_2-1은 기존 WALL 템플릿을 인스턴스한 SS2D 지형이었다. 아스트라는 지형 배치를 새로 굽지 않고, 그 인스턴스 루트의 script와 shape_material을 씬에서 오버라이드했다.

기존 템플릿:

- `scenes/집/스마트 매쉬 assets/WALL_벽체/TEMPLATE_WALL_SOLID.tscn`
- `scenes/집/스마트 매쉬 assets/WALL_벽체/TEMPLATE_WALL_SOLID_WHITE.tscn`

템플릿 기본 스크립트는 `scripts/스마트월드/지형.gd`다. 현재 stage_2-1의 36개 지형은 `scripts/스마트월드/하수도_자연발판.gd`로 오버라이드되어 있다. 템플릿에는 점/재질/저장된 _meshes/충돌 자식도 있다. 이 **기존 PackedScene 위에서 스크립트를 교체한 구조**가 중요한 조사 대상이다.

현재 분류:

- 공중형 8개: A_L2, A_L3, A_L4_착지대, B_G1_함정발판, B_G2_마른발판, B_S2_유령칸, B_F1_선반, C_G3_검정물_발판.

- 공중형에는 `석조선반 = true`, 땅형에는 `땅지형 = true`가 설정되어 있다.

**기존 사각형으로 돌려놓거나 모든 지형을 하나의 프리팹 크기로 바꾸지 말 것.**

먼저 루트 AGENTS.md / CLAUDE.md와 `docs/다음작업_프롬프트.md`를 읽고 현재 규약을 확인한다.

상속 관계:

```text
addons/rmsmartshape/shapes/shape.gd (SS2D_Shape)
  → SS2D_Shape_Closed
	→ scripts/스마트월드/지형.gd
	  → scripts/스마트월드/하수도_벽돌지형.gd
		→ scripts/스마트월드/하수도_자연발판.gd
```

집중해서 읽을 부분:

1. `addons/rmsmartshape/shapes/shape.gd`
   - set_point_array: 기존 _points에서 연결 해제 후 새 _points에 두 신호 연결.
   - _set_material: 기존 shape_material에서 연결 해제 후 새 재질에 changed 연결.
   - 현재 코드는 **기존 리소스에서의 해제 여부는 확인하지만 새 리소스에 이미 연결돼 있는지는 확인하지 않고 connect**한다.

2. `scripts/스마트월드/지형.gd`
   - _ready: _meshes.clear(), super(), force_update(), 에디터일 때 return, 런타임 _셰이더_설치 등의 순서.

3. `scripts/스마트월드/하수도_벽돌지형.gd`

   - AtlasTexture를 ImageTexture로 변환하는 처리, 흑백 짝 메타데이터, 부모 셰이더 설치 호출.
4. `scripts/스마트월드/하수도_자연발판.gd`
   - 부모가 만든 ShaderMaterial의 shader를 자연형/선반으로 교체한다.
   - ground_platform, surface_bounds, ground_edges, ground_cap_tex를 준비한다.
5. stage_2-1과 원본 WALL 템플릿을 함께 읽는다.
   - 인스턴스 script 교체가 리소스 setter/기존 신호 연결에 어떤 영향을 주는지 확인한다.

## 5. 확인된 사실과 가설을 구분하라

확정:

- 세 connect 호출에서 이미 연결된 동일 callable에 재연결을 시도한다.
- 같은 오류가 36회씩 발생하고 대상 스크립트는 하수도_자연발판.gd다.
- 지형 수 36개와 반복 횟수가 일치한다.
- 현재 stage_2-1은 기존 템플릿 인스턴스에 스크립트를 교체하는 구조다.

유력하지만 미확정:

- 인스턴스 스크립트 교체/역직렬화/리소스 재대입 중 연결 상태가 남아 있어 setter가 동일 연결을 다시 시도한다는 설명.
- 재질 복제가 changed 신호 연결 상태 또는 재진입에 영향을 주는지 여부.

아직 증명하지 않은 말을 완료 보고에 원인으로 확정해서 쓰지 않는다. setter가 호출될 때 이전 리소스와 새 리소스의 instance_id, 동일성, 새 리소스의 is_connected, 노드 script 경로를 비교하면 원인을 좁힐 수 있다. 임시 진단은 필요한 횟수만 기록하고 배포 코드에 과도한 로그를 남기지 않는다.

## 6. 수정 가능한 범위와 우선순위

### 직접 수정 가능한 곳

- 원인이 확인된 `shape.gd`의 set_point_array/_set_material 주변 연결 관리.
- 하수도_벽돌지형.gd / 하수도_자연발판.gd의 초기화나 리소스 처리 중 실제 원인이 확인된 부분.
- 동일 오류가 나지 않는 하수도 전용 기본 템플릿이 필요하다고 증명되면 새 템플릿을 만들고 stage_2-1의 인스턴스 연결을 조정할 수 있다.
- 재현/회귀 확인용 작은 테스트와 작업기록.

### 우선 검토할 최소 수정

새 리소스에 connect하기 전에 **그 새 리소스와 정확히 같은 callable**의 연결 여부를 검사하는 방식이다. 이미 연결되어 있으면 다시 연결하지 않는다. 이는 연결 동작을 여러 번 호출해도 결과가 같게 만드는 처리다.

단, guard 몇 줄 넣고 끝내지 말고 아래를 확인한다:

- 연결이 없는 경우에는 실제로 연결되는가?
- 리소스 A에서 B로 바꾸면 A의 자기 연결은 해제되는가?
- B에 미리 자기 연결이 있으면 하나만 유지하는가?
- 다른 노드가 공유 리소스에 연결한 신호를 해제하지 않는가?
- null point array를 새 리소스로 대체하는 동작과 null material 동작을 유지하는가?
- set_as_dirty / notify_property_list_changed가 유지되는가?
- 동일 값을 다시 설정해도 편집기 갱신에 필요한 처리를 빠뜨리지 않는가?

무조건 `if old == new: return`으로 모든 후처리를 건너뛰는 것은 근거 없이 적용하지 않는다. 일괄 disconnect, CONNECT_REFERENCE_COUNTED로 오류만 우회, block_signals, 오류 출력 필터링, 초기화 함수 삭제는 해결책이 아니다.

### 영향 범위가 큰 곳

SS2D 애드온은 스테이지1 등 다른 팀원이 사용하는 공용 코드다. 애드온 전체 교체/업데이트/광범위 리팩터링은 하지 않는다. 국소적인 중복 연결 방어를 고쳤다면 일반 SS2D 템플릿도 회귀 검증한다.

원본 WALL 템플릿을 하수도 전용 스크립트나 아트로 바꾸지 않는다. 다른 맵이 영향을 받는다. 새 기본 템플릿을 쓰는 방식이라면 현재 지형별 점·원점·상태·충돌 경로를 모두 보존하는 비교가 필요하다.

## 8. 안전 규칙과 작업 순서

1. `git status --short`와 대상 파일 diff를 먼저 확인한다. 작업 트리에 여러 사람의 미커밋 변경이 있다. HEAD와 다르다는 이유로 복구/초기화하지 않는다.
2. 최신 로그를 읽고 오류 종류별 횟수를 다시 집계한다. 엔진을 실행하지 않아도 기존 로그는 읽을 수 있다.
3. 필요한 파일만 읽고 근본 원인 가설을 세운다.
4. 현재 수정 대상 파일의 작업 시작 시점 사본 또는 내용을 별도 보관하고, 최종 diff는 그 상태와 비교한다. 사용자 파일을 덮어쓴 백업으로 만들지 않는다.
5. 최소 수정하고, 왜 필요한지 한글 코드 주석을 추가한다.
6. 정적 검사와 필요한 엔진 검증을 구분해 수행한다.
7. 작업기록과 결과를 남긴다.

저장소의 Godot 안전 규칙:

**사용자가 Godot 실행을 명시적으로 허용하기 전에는 편집기·콘솔·headless·빌드 도구를 실행하지 않는다.** 이 MD를 전달받은 것만으로 실행 권한을 새로 받았다고 해석하지 말고, 해당 작업 대화에서 이미 허용됐는지 확인한다. 허용되지 않은 상태에서도 코드 분석·수정·정적 검증은 진행할 수 있다. 실행 필요 시 실제로 준비된 수정과 검증 계획을 설명하고 명시적 실행 허용을 받는다. 단순히 어려운 작업이라는 이유로 승인을 반복 요청하지 않는다.

허용된 경우 엔진은 `C:/Users/Public/godot46/`의 Godot 4.6.3을 사용한다. 한글 경로의 console exe 문제를 피하기 위한 위치다. 최신 로그에는 Compatibility/OpenGL 실행이 기록되어 있으므로 프로젝트 파일의 Forward Plus 표기만 보고 시험 렌더러를 단정하지 않는다. 엔진 실행 시 프로젝트를 명확하게 지정하고 `--disable-crash-handler`를 사용한다. 실행과 종료가 불확실한 프로세스를 여러 개 띄우지 않는다.

`tools/build_*.gd` 등 씬 전체 재생성은 하지 않는다. 읽어온 노드의 owner를 재설정하지 않는다. .godot 삭제, 전역 캐시 초기화, 전체 씬 재저장, git reset/clean, 자동 커밋/푸시는 이번 범위가 아니다.

## 9. 검증 계획 — 숫자만 맞추지 말 것

### 정적 검사

- 새 리소스의 연결 여부를 올바른 callable로 확인하는지.
- 이전 리소스 해제와 새 연결, null 처리, dirty 갱신이 유지되는지.
- 지형 인스턴스/상태/색/물 장치/배경이 불필요하게 변경되지 않았는지.
- `git diff --check`.
- graphify 사용 규약이 적용되면 따르되 실패를 숨기지 않는다. 이전 세션에는 graph.json이 없고 graphify 실행 경로 문제가 있었다. 현재 상태를 다시 확인한다.

### 엔진 실행이 허용된 경우의 최소 재현 테스트

다음은 테스트 설계이며 그대로 붙여 넣는 완성 코드가 아니다. 실제 타입/메서드와 test harness를 확인해 작성한다.

1. 일반 SS2D 하나에 점 리소스 A를 설정하고 같은 A를 다시 설정한다.
2. 새 점 리소스 B에 이 노드의 대상 신호를 미리 연결한 뒤 B로 바꾼다. 연결 수가 늘어나지 않아야 한다.
3. A의 신호는 더 이상 그 노드를 호출하지 않고 B는 한 번 호출해야 한다.
4. 재질 A/B에 대해서도 같은 검증을 한다.
5. 공유 리소스에 다른 노드가 연결된 경우 그 연결은 유지되어야 한다.
6. null과 빈 리소스 처리도 확인한다.
7. stage_2-1을 새로 로드하여 처음부터 끝까지 로그를 캡처한다. 테스트 시작 로그와 이전 누적 로그를 혼동하지 않는다.
8. 씬을 해제한 뒤 다시 로드해도 같은 오류가 재발하지 않아야 한다. 임의로 여러 번 연결했다가 오류 로그를 지우는 방식은 금지다.

### 기능/외관 회귀

- 일반 WALL, 흰색 WALL, 하수도 공중형, 하수도 땅형을 각각 확인한다.
- 에디터에서 SS2D 점 수정 후 외관/충돌 갱신, 재질 변경, 저장 후 재열기를 확인한다.
- runtime에서 흑백 선반이 사라지지 않고 상면/지지대가 유지되는지.
- 흰색/검정 칠하기·회수·부분 칠·반대색 접촉·유령 발판 상태가 유지되는지.
- 관련 검사 `tools/test_하수도_벽돌_색칠사망.gd`는 과거132개 검사였지만 새 선반 표현 전용 테스트는 아니다. 이 검사만 통과했다고 이번 외관/중복 신호를 검증한 것으로 보지 않는다.
- 공용 shape.gd를 수정했다면 `docs/다음작업_프롬프트.md`의 현재 필수 검사 범위를 확인한다. 오래된 문서의 검사 수를 복사해 전부 실행했다고 보고하지 않는다.

### 남은 8건

사용자 디버거의 오류/경고 필터와 항목 내용을 확보한다. 최신 runtime log에 없다면 편집기 항목의 메시지와 파일/줄을 별도로 확인한다. 메시지를 얻을 수 없으면 “108건의 원인은 확인/수정, 나머지8건 미확인”처럼 분리해 보고한다. 8건 모두를 경고라고 가정하지 않는다.

## 10. 로그 집계 예시 — 읽기 전용

PowerShell에서 기존 로그 집계:

```powershell
$taskLogPath = 'C:/Users/아버지/AppData/Roaming/Godot/app_userdata/dev_4/logs/godot.log'
$taskLogLines = Get-Content -LiteralPath $taskLogPath
$taskLogLines |
	Where-Object { $_ -match '^(ERROR|SCRIPT ERROR|SHADER ERROR|WARNING):' } |
	Group-Object |
	Select-Object Count, Name |
	Format-List
```

읽기 권한이 막히면 허용된 파일 읽기 권한 절차를 이용한다. 로그 접근 실패를 오류가 없다는 뜻으로 해석하지 않는다.
