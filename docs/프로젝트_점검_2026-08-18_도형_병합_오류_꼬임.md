> 요청: "내가 만든 파일과 현재 깃에 올라간 파일을 합쳐서 작업을 시작하고 싶어."

## 0. 세 줄 요약

1. **합칠 것이 없다.** zip 은 지금 GitHub `dev_4` 보다 **뒤쳐진 사본**이다.

2. 게임은 **정상 작동**한다. 자동 검사 13 종 전부 통과(엔진을 4.6.3 으로 올린 상태에서도).
   사망 판정도 실제 씬에서 도는 것을 확인했다(§3).
3. 실제로 고친 문제 4 건, 새로 알아 둘 함정 3 건이 있다. 아래 §2·§4.

## 1. 병합 판정 — 왜 "합칠 것이 없다" 인가

### 1-1. 무엇을 비교했나

zip 의 `.git` 이 살아 있어서 **추측이 아니라 커밋 그래프로** 비교했다.

```
zip 의 HEAD        : 72dde6c  "인수인계 문서 갱신 — 다음 작업자용 프롬프트"
GitHub dev_4 HEAD  : 6df5076  (merge) ← 72dde6c 의 자손
공통 조상          : 72dde6c   (= zip 의 HEAD 그 자체)
```

zip 의 작업 트리를 임시 커밋으로 굳혀 `dev_4` 와 diff 한 결과:

| 방향 | 파일 | 내용 |
|---|---|---|
| GitHub 에만 있음 | `scripts/ui/페인트_HUD*.gd` (4개) | 점(pip) 방식 HUD — 커밋 `0cb03a5` |
| GitHub 에만 있음 | `CLAUDE.md`, `docs/작업기록_2026-08-17_페인트HUD_점방식.md` | |
| GitHub 에만 있음 | `stage_1-1, 1-2.tscn` 의 **UID 복원** | 커밋 `fe56984` |
| zip 에만 있음 | — **없음** | zip 쪽 차이는 전부 위 작업들의 **이전 상태**였다 |

즉 zip → GitHub 은 **한 방향 진행**이다. 되돌릴 것이 하나도 없다.

### 1-2. zip 안의 "미커밋 작업"은 이미 올라가 있다

zip 작업 트리에는 커밋 안 된 변경이 25 건 있었다
(`카메라_공간.gd`, `카메라공간배치.gd`, `지형_다듬기.gd`, `proto_camera.gd` …).
전부 GitHub 의 커밋 `e5f1120 "카메라 공간(굴뚝 심리스 전환) + 공중 지형 뿌리내리기"` 와 같은 내용이다.
→ 도형님이 zip 을 만든 **뒤에 커밋·푸시**한 것으로 보인다.

### 1-3. ⚠ zip 을 다시 풀 일이 있다면 — 한글 파일명이 조용히 사라진다

`color (2).zip` 을 Windows 탐색기로 풀면 **한글 이름 파일 228 개가 통째로 깨진다.**
(`docs/게임_기획서…md` → `docs/寃뚯엫_湲고쉷…md`)

- 원인: zip 은 파일명을 **UTF-8** 로 저장했는데, 탐색기가 **CP949** 로 읽는다.
- 무서운 점: 에러가 안 난다. 폴더는 생기고 파일만 없다 —
  `docs/` 폴더가 **비어 있는 채로** 만들어졌다.
  이 상태로 `git status` 를 보면 **228 개가 `D`(삭제)로 잡힌다.**
  그대로 커밋하면 `2026-08-07` 사고(남의 작업 55 개 소실)가 그대로 재현된다.
- 안전한 해제법 (PowerShell, UTF-8 지정):

```powershell
Add-Type -AssemblyName System.IO.Compression, System.IO.Compression.FileSystem
$fs = [System.IO.File]::OpenRead("C:\...\color (2).zip")
$z  = New-Object System.IO.Compression.ZipArchive($fs, [System.IO.Compression.ZipArchiveMode]::Read, $false, [System.Text.Encoding]::UTF8)
# … 항목별 ExtractToFile
```

> **결론: zip 은 백업으로만 두고 열지 말 것.** 작업은 `Documents/GitHub/color` (dev_4) 에서 한다.

## 2. 실제로 발견하고 고친 문제

### 2-1. ★`스마트월드_4` 의 출구가 끊길 뻔했다 — **고쳤음**

- 증상: 챕터표에 스테이지를 새로 넣었더니 `test_챕터전환` 이 `55/56` 으로 깨졌다.
  `스마트월드_4 출구 → 5 번` 이어야 하는데 `1 번` 을 가리키고 있었다.
- 원인: **"다음 스테이지" 는 챕터표에서 계산되는데, 그 계산 결과는 씬 파일에 구워져 있다.**
  표를 고쳐도 씬을 다시 굽지 않으면 옛 목적지가 남는다.
  마지막 스테이지는 "표의 첫 줄로 되돌아가기" 라, 첫 줄이 바뀌면 마지막 스테이지도 바뀐다.
- 조치: `스마트월드_4.tscn` 의 `다음_씬` 한 줄만 `스마트월드_5.tscn` 으로 고쳤다.
  (씬을 통째로 다시 굽지 않았다 — 그러면 에디터 편집분이 날아간다)
- **앞으로**: 챕터표의 **순서**를 바꾸면 항상 `test_챕터전환` 을 돌릴 것. 이 검사가 유일한 안전망이다.

### 2-2. 문서에 적힌 엔진 경로가 없다 — **문서 갱신 필요**

`docs/다음작업_프롬프트.md` §1 의 복붙 블록이 가리키는 경로가 이 PC 에 없다.

```
없음 : C:\Users\김도형\OneDrive\Desktop\Godot_v4.6-beta2_win64.exe\...
있음 : C:\Users\김도형\Desktop\Godot_v4.6.3-stable_win64.exe          (본체)
있음 : C:\Users\김도형\Downloads\Godot_v4.6.3-stable_win64.exe\..._console.exe (콘솔)
```

**★함정 2 개가 같이 있다:**

1. **콘솔 exe 와 본체 exe 가 다른 폴더에 있으면 안 된다.**
   콘솔 exe 는 같은 폴더의 본체를 찾아 다시 띄우는 얇은 껍데기다.
2. **★콘솔 exe 는 경로에 한글이 있으면 본체를 못 찾는다.**
   `Main executable C:\Users\\Downloads\...exe not found` —
   보다시피 사용자 이름 `김도형` 이 **통째로 사라진 채** 찾는다.
   → 검사를 돌리려면 **ASCII 경로에 두 exe 를 같이 복사**해야 한다.

```powershell
# 한 번만 해 두면 된다
New-Item -ItemType Directory -Force C:\Users\Public\godot46
Copy-Item "$env:USERPROFILE\Desktop\Godot_v4.6.3-stable_win64.exe"                     C:\Users\Public\godot46\
Copy-Item "$env:USERPROFILE\Downloads\Godot_v4.6.3-stable_win64.exe\*_console.exe"     C:\Users\Public\godot46\
```

이후 검사 명령:

```bat
set G=C:\Users\Public\godot46\Godot_v4.6.3-stable_win64_console.exe
%G% --headless --path "C:\Users\김도형\Documents\GitHub\color" -s res://tools/check_스마트월드.gd
```

(프로젝트 경로에 한글이 있는 것은 **문제없다** — 깨지는 건 콘솔 껍데기의 exe 탐색뿐이다.)

**4.6-beta2 → 4.6.3-stable 로 올려도 회귀 없음**: 검사 13 종 전부 통과했다.

### 2-3. 체인 빌더에 "일부만 굽기" 가 없었다 — **기능 추가**

`tools/스마트월드_체인.gd` 는 **표에 있는 스테이지를 전부** 다시 구웠다.
스테이지를 하나 추가할 때마다 기존 4 개가 같이 다시 구워져, CLAUDE.md 규칙 4
("에디터에서 손본 값이 전부 날아간다") 를 지킬 방법이 없었다.

→ `-- --만 5,6,7` 인자를 추가했다. 안 주면 예전과 완전히 같다(회귀 없음).

```bat
%G% --headless --path . -s res://tools/스마트월드_체인.gd -- --만 5,6,7
```

### 2-4. 새 스크립트의 `class_name` 은 헤드리스에서 못 쓴다 — **다시 확인됨**

이미 `월드.gd` 머리말에 적혀 있는 함정인데, 이번에도 그대로 터졌다.

```
SCRIPT ERROR: Parse Error: Could not find type "빛기둥" in the current scope.
```

전역 클래스 이름은 **에디터가 프로젝트를 한 번 훑어야** 등록된다.
헤드리스 검사(`-s tools/…`)는 그 등록을 안 하므로 파싱 단계에서 통째로 죽는다.

→ **새 스크립트끼리 참조할 때는 `class_name` 대신 경로 `preload`** 를 쓴다.
이번에 만든 `창문커튼.gd` · `build_원본_집.gd` 전부 그렇게 했다.
(에디터를 한 번 열면 등록되지만, **CI/헤드리스에서 죽는 코드는 만들지 않는 것**이 규약이다.)

## 4. 새로 알아 둘 함정 (지뢰밭에 추가할 것)

### 4-1. ★"레벨검사는 지형만 본다" — 물감에 의존하는 길은 소프트락으로 잡힌다

이번에 만든 **빛다리**는 물감을 쏴야 굳는다. 즉 **처음에는 지형이 아니다.**
`레벨검사.gd` 는 지형만 훑으므로, 빛다리를 유일한 길로 쓰면
`✖ 여기 들어가면 출구까지 못 간다` 로 잡힌다 — 팀의 품질 게이트가 빨개진다.

→ **지금은 빛다리를 "빠른 길", 지형을 "느린 길" 로 둘 다 뚫어 두었다.**
   (거실: 구덩이 아래로 돌아가는 계단 / 지붕: 가로막이 옆 가구 계단)
→ **다음 작업 후보**: `레벨검사.gd` 가 `빛기둥`(발판 모드)을 지형으로 세게 만들면,
   그때 빛다리를 진짜 자물쇠로 바꿀 수 있다.

### 4-2. ★`_ready()` 에서 그룹에 등록하면 안 되는 경우가 있다

`빛기둥` 은 경계 모드일 때만 그룹 `빛경계` 에 들어가야 한다.
그런데 `창문커튼` 은 자식 빛을 `new()` → `add_child()` → **그 다음에** 모드를 준다.
`_ready()` 는 `add_child()` 순간에 이미 도므로, **그때의 모드는 기본값**이다.
→ 발판으로 쓸 빛이 `빛경계` 에 남아 스테이지의 경계 빛이 3 개가 아니라 4 개로 잡혔다.

**눈으로는 절대 안 보인다** — 발판 모드 빛은 `위험한가()` 가 항상 false 라 조용하다.
→ **모드처럼 나중에 바뀔 수 있는 값으로 그룹을 정한다면, 그 값이 바뀔 때마다 그룹도 맞춘다.**
   (`빛기둥._그룹_맞추기()` 참고. `test_빛창문` [H] 가 이걸 잡아냈다)

### 4-3. ★카메라 리밋만으로는 "벽 바깥"을 못 가린다 — **벽을 두껍게** 만들어야 한다

굴뚝 벽을 200px 로 만들었더니, 굴뚝 안에서 **벽 너머 빈 공간이 그대로 보였다.**
(도형님이 "맵의 벽을 넘어가지 않으면 좋겠다" 고 한 바로 그 그림)

리밋은 **카메라의 위치**를 묶을 뿐 **화면 크기**는 안 바꾼다.
줌 0.82 × 카메라공간 배수 1.34 = 1.10 → 화면 폭 **1745px** 인데 굴뚝 안쪽은 **500px** 이다.
남는 1245px 은 무조건 벽 자리다.

→ **벽 두께 ≥ 화면 반폭**(여기서는 1400px)으로 만든다.
  림보·레인월드가 쓰는 방식 그대로 — "공간은 덩어리에서 파낸 것" 이어야 벽 너머가 없다.
  ⚠ **안쪽 면 좌표는 그대로 둔다.** 거기가 `카메라공간배치.gd` 의 기준이다.
