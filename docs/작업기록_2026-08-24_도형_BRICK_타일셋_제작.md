## 1. 시작 상태 — BRICK 원본이 없었다

프로젝트의 brick 에셋을 전부 실측한 결과 마스터 템플릿 규격에 맞는 원본이 없었다.

| 파일 | 실측 | 규격 | 판정 |
|---|---|---|---|
| `black_brick_edge.png` | 128×24, 알파 없음, 평균 4.1 | 1024×256 알파 실루엣 | ❌ 픽셀아트 |
| `black_brick_fill.png` | 128×128, 알파 없음 | 1024×1024 | ❌ 8배 부족 |
| `assets/tileset/brick.png` | 768×768 = 블록 4개(349×332) | 띠 텍스처 | ❌ 블록 스프라이트 |

`.godot/imported` 에 `black_brick_top/left/tl/...` 흔적이 있으나 원본 PNG 는 전부 삭제된 상태.
`brick.png` 에서 띠를 뽑으려면 가로 2.93배 확대가 필요해 일러스트가 아니라 뭉갬이 된다.

→ 사용자 판단으로 **원본 4장을 AI 로 생성**했다 (마스터 템플릿 §3-1 이 허용하는 경로.
  ★ 코너는 여전히 AI 로 그리지 않고 엣지 단면에서 합성한다).

생성 조건은 파이프라인 입력 규격을 grass 원본에서 실측해 정했다:
중간톤 그레이스케일(평균 ~70) · 좌우 타일링 · 배경 키잉용 단색 마젠타 · 평면 정사 투영.

결과 원본: `tools/brick_v1_pipeline/src/master_{top,bottom,side,fill}.png`
(2752×1536 ×3, 2048×2048 ×1). 좌우 이음매 1.00~2.61 **전부 PASS**,
fill 은 상하까지 0.82 PASS.

## 2. Python 문제 — 설치 불필요로 결론

`apply_final.py` 가 쓰는 연산을 전부 열거했다:

```
numpy 산술 / power(감마) / percentile / hypot·arctan2(코너 극좌표)
FLIP_LEFT_RIGHT / tile 3x3 / LANCZOS resize / GaussianBlur
```

- Godot 에 없는 건 **GaussianBlur 하나**뿐 → 분리형 순환 블러 20줄로 이식
- `Image.INTERPOLATE_LANCZOS = 4` / `blit_rect` / `get_region` 은 실제 호출해 동작 확인
- 코너 극좌표 합성은 이전 세션에 이미 GDScript 로 재구현해 **잔차 1.00/255** 확인 완료
- ★ 픽셀 단위 동일성은 요구되지 않는다 — grass_v4 산출물은 LOCK 이라 다시 굽지 않는다

→ `tools/생성_타일셋_파생.gd` 하나로 통일. 실행 8.5초.

## 3. 재질별로 새로 정해야 했던 것 3가지

마스터 템플릿에 §9-B 로 반영했다.

### (1) 감마 2.80 (grass 는 1.60)
grass 원본은 평균 70 이라 1.60 이면 31 이 되지만, brick 원본은 평균 ~140 이라
1.60 으로는 76 밖에 안 내려간다. **맞춰야 하는 것은 감마가 아니라 BLACK 평균 31.**

| 감마 | BLACK | 엣지 단계 | 필 단계 | WHITE |
|---|---|---|---|---|
| 1.60 | 76.53 | 66 | 103 | 178.5 |
| 2.20 | 49.32 | 56 | 81 | 205.7 |
| **2.80** | **32.00** | **45** | **60** | **223.0** |
| 3.40 | 20.84 | 35 | 44 | 234.2 |

2.80 은 grass(31.25 / 223.75)와 사실상 같은 검정·흰색이면서
내부 디테일은 45~60단계로 grass 의 12단계보다 4~5배 넓다 — 줄눈 구조가 살아난다.

### (2) 코너 방식 `miter` (grass 는 `polar`)
polar 는 띠를 코너에 감아서 **줄눈이 부채꼴로 휜다.** 직선 줄눈과 절대 안 맞는다.
miter 는 두 띠를 직선 그대로 두고 45도에서 섞는다.
※ 이음매 수치는 둘이 거의 같았다(18.0 vs 17.6). **고른 이유는 수치가 아니라 줄눈이 직선으로 남는 것.**

### (3) ★ 띠 기준선을 중앙값으로 — 이게 제일 크게 먹혔다
띠를 자를 기준을 '가장 뾰족한 봉우리' 로 잡았더니, 골이 깊은 벽돌 윗면 때문에
엣지의 **40.7% 가 투명**(잔디 21.5%)이 되었다.
그 빈 구간을 코너 합성이 코너 전체로 퍼뜨려 **반투명한 벽돌 유령 블록**으로 렌더됐다.

**열별 실루엣의 중앙값**으로 바꾼 뒤:

| | 이전 | 이후 |
|---|---|---|
| 엣지 투명 비율 | 40.7% | **25.8%** |
| 코너 불투명 비율 | 20.7% | **39.2%** |
| 오목 코너 이음매 | 29.86 | **9.42** |
| 볼록 코너 이음매 | 17.64 | **15.83** |

## 4. 최종 수치

열평균 단차 (/255, 배경 제외 · 양쪽 열 모두 지형인 행만)

| | 대조군(직선) | 볼록 | 오목 |
|---|---|---|---|
| grass_v4 | 2.77 | 6.90 (2.5배) | 6.14 (2.2배) |
| **brick_v1** | **6.86** | **15.83 (2.3배)** | **9.42 (1.4배)** |

- 벽돌은 줄눈 때문에 **직선 구간에서도 6.86** 이 나온다. 절대값 6 을 요구할 수 없다.
- 대조군 대비 배수로 보면 볼록 2.3배 / 오목 1.4배 로 **grass(2.5 / 2.2)와 같거나 낫다.**
- 코너 구간 디테일 비율은 0.56 / 0.45 로 grass(1.5~2.9)보다 낮다 — 코너에서
  줄눈이 흐려지는 것은 남아 있다. **미해결로 기록한다.**

색상: BLACK 32.00 / WHITE 223.0 / 대비폭 191.0 (grass 31.25 / 223.75 / 192.5)

## 5. 측정 도구의 함정 — 같은 종류로 세 번 헛짚었다

1. **열 평균에 배경을 포함**하면 볼록 코너 바깥에서 '도형이 끝난 것' 을 이음매로 오인한다.
   벽돌에서 20~35/255 의 가짜 값이 나왔다. → 양쪽 열 모두 지형인 행만 평균한다.
   (잔디는 실루엣이 부드러워 이 오염이 안 보였다. 잔디 수치도 이 수정 뒤 4.55→6.90 으로 정정됐다.)
2. **밝기 통계를 알파>127 로 필터**하면 낮은 알파의 이상 픽셀을 통째로 놓친다.
3. **눈으로 "밝은 블록" 이라 판단하기 전에 픽셀값을 찍어라.**
   벽돌 코너의 '밝은 사각형' 은 실제로는 배경(0.659)보다 **어두운** 0.50~0.65 였다.
   검은 지형 옆이라 밝아 보였을 뿐, 원인은 밝은 색이 아니라 **알파 부족**이었다.
   → 이걸 확인하기 전까지 디스필·언프리멀티플라이 가드로 두 번 헛수고했다
     (둘 다 수치가 소수점 둘째 자리까지 그대로였다 = 원인이 아니라는 증거였는데 놓쳤다).

## 7. 남은 것 (BRICK)

1. **코너 디테일 비율 0.45~0.56** — 코너에서 줄눈이 흐려진다.
   원인은 코너 텍스처가 256px 로 엣지(1024px)보다 성기게 샘플링되기 때문으로 보이나
   **아직 수치로 확정하지 않았다.** 다음 작업에서 코너 해상도 512 를 시험해 볼 것.
2. **SIDE 마스터의 방향** — AI 가 '길이 방향으로 벽돌 끝면이 반복되는 띠' 대신
   기둥이 있는 벽면을 그렸다. 세로 벽에서 기둥이 가로 단(段)으로 읽혀 나쁘지 않지만
   의도한 그림은 아니다. 재생성하면 더 나아질 여지가 있다.
3. **실제 스테이지 적용은 안 했다.** 지시대로 테스트 씬에서만 완성했다.
