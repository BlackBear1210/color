# 작업기록 2026-08-17 — 페인트 HUD 를 글씨에서 점(pip)으로

> 대상: **스마트월드 6개 씬** + **`stage_1-1, 1-2.tscn`**
> (스테이지_1~5 · zone_* · 동현 테스트월드는 폐기 대상이라 손대지 않음)

---

## 1. 왜 했나

예전 HUD 는 좌상단 글씨 한 줄이었다.

```
페인트 8 / 12   (회수대기 3)   [회색으로 잠김 2발]
```

문제가 셋이었다.

| # | 문제 | 왜 문제인가 |
|---|---|---|
| ① | 핵심 자원을 **문장으로 읽게** 만든다 | 한눈에 안 들어온다 |
| ② | "회수대기 3" 의 3 이 **발 수가 아니라 대상 개수**였다 | `회수_대기수()` 가 줄 길이를 돌려준다. 옆 숫자는 전부 발 단위라 플레이어는 "3발"로 오해한다. 대상 하나가 3발을 먹고 있어도 화면엔 **1** 로 뜬다 |
| ③ | FIFO(규칙 4) 가 **눈에 안 보인다** | E 가 "무엇이 풀릴지 모르고 누르는 키"였다. 칠한 발판을 되돌리면 그 발판이 실제로 사라지므로, **밟고 선 것을 회수해 추락**하는 사고가 난다 |

`페인트_코어.gd` 에 `다음_회수대상()` 이 "HUD 하이라이트용"으로 이미 있었는데
**아무 데서도 쓰지 않고 있었다.** ③ 은 함수를 새로 짤 필요조차 없었던 공백이다.

## 2. 무엇이 되었나

### 탄약 줄 (좌상단)

총량을 **칸 수로 고정**해 그린다. 칸이 사라지지 않고 상태만 바뀌므로
"내 페인트가 지금 어디에 가 있나"가 한 줄로 읽힌다.

| 모양 | 뜻 | 언제 돌아오나 |
|---|---|---|
| 꽉 찬 점 (내 색 채움 + 반대색 링) | 지금 쏠 수 있는 발 | — |
| **점선 링** | 칠하는 중 (아직 완성 아님) | 완성돼야 회수 대상이 됨 |
| 빈 점 | 회수 대기 | E |
| 빗금 친 점 | 회색 잠김 | 스테이지 이동 / 사망 |
| 흐린 빈 칸 | **어디에도 없는 발** (§5 참고) | 안 돌아옴 |

회수 대기 칸은 **대상별로 묶는다.** 묶음 사이만 넓게 띄우면 글씨 없이
"대상 3개, 각각 2·3·1발"이 읽힌다. 라벨은 일부러 안 붙였다 — 대상이 몇 개만 돼도
줄이 무너지고, 대상 이름은 어차피 화면 안에 있다.

### 색을 어떻게 정했나 — 여기가 제일 까다로웠다

- 흰색으로 그리면 **"흰 페인트 잔량"으로 오해**한다.
- **회색은 더 나쁘다.** 이 게임에서 회색은 "죽은 색 · 복구 불가"라 정반대 의미가 된다.
- → 찬 점은 **지금 내 색으로 채우고 링은 반대색**으로 두른다.
  쏘면 정말 그 색이 나가므로 오해가 아니라 **사실**이고,
  Shift 로 색을 바꾸면 칸이 한꺼번에 뒤집혀 **색 전환 자체에 피드백이 생긴다**
  (지금까지 색 전환은 캐릭터 스프라이트 말고 알려주는 게 없었다).
- 회수 대기·잠김 링은 플레이어 색과 **무관하게 밝은 저알파**로 그린다.
  반대색으로 그리면 흰 플레이어일 때 검은 링이 어두운 받침에 묻혀 사라진다.
- 점마다 **어두운 받침 원**을 깔아 밝은 지형 위에서도 안 묻히게 했다.
  (2026-07-22 조준 궤적이 "어두운 링 + 밝은 코어"로 푼 것과 같은 문제·같은 해법)

### 월드 마커

- **E 마커** — 다음에 회수될 대상 위. 아래에 돌아올 발수를 점으로.
  ★마커 위치는 노드 좌표가 아니라 **마지막으로 칠한 지점**이다.
  SS2D 지형은 원점이 도형 한쪽 끝이라 노드 좌표를 쓰면 마커가 지형 저 멀리에 뜬다.
  이걸 위해 `_회수줄` 항목에 `"좌표"` 를 추가했다.
- **호버** — 대상에 마우스를 얹으면 그 대상에 **몇 발 들어갔는지** 그 자리에 뜬다.
  "몇 발 썼지?"는 화면 구석이 아니라 그 대상 옆에 있어야 하는 정보다.
  판정은 `총알.gd` 와 **같은 레이어·같은 방식**(점 조회 + 통과형 Area + 덤불)을 쓴다.
  다르면 호버 표시가 거짓말이 된다.

## 3. 구조 — HUD 하나 + 어댑터 둘

살아 있는 색칠 시스템이 둘이고 API 가 다르다. HUD 를 두 벌 만들면 같은 버그를
두 번 고쳐야 하므로, **그리는 코드는 하나**로 두고 읽어오는 방법만 갈아끼운다.

```
scripts/ui/페인트_HUD.gd              ← 그리기 전담 (CanvasLayer)
scripts/ui/페인트_HUD_어댑터.gd        ← 공통 창구(인터페이스)
scripts/ui/페인트_HUD_어댑터_코어.gd   ← 페인트코어용 (스마트월드)
scripts/ui/페인트_HUD_어댑터_타일.gd   ← TilePaintMap용 (stage_1-1, 1-2)
```

`스마트월드/` 도 `proto/` 도 아닌 `ui/` 에 둔 이유: 양쪽에서 쓰기 때문이다.
어느 한쪽에 두면 나중에 그 폴더를 정리할 때 같이 딸려 간다.

### 두 시스템의 실제 차이 (알고 있어야 함)

| | 페인트코어 (스마트월드) | TilePaintMap (stage_1-1, 1-2) |
|---|---|---|
| 탄약 | **12발** (스테이지마다 다름) | **14발** (§8 에서 신설) |
| 회수줄에 들어가는 것 | 부분 색칠(progress)**도** 들어감 | **완성된 것만** 들어감 |
| 발수의 의미 | 자원 1발 | 그 플랫폼의 크기(필요횟수) |
| 잠김 표시 | 잠긴 발 수 | 잠긴 발 수 (무제한 설정이면 회색 플랫폼 **개수**) |

★마지막 줄이 중요하다. 타일맵 쪽 `맞은` 은 자원이 아니라 크기라 값이 10 을 넘는다.
발수대로 점을 찍으면 **플랫폼 두 개만 칠해도 점이 22 개**가 되어 줄이 화면을 가로지른다
(실제로 첫 스크린샷에서 그렇게 나왔다).
→ 어댑터의 `발수를_센다()` 가 거짓이면 **대상 하나에 점 하나**로 접는다. 발수는 호버로 본다.

## 5. ⚠ 하다가 밟은 것 — 다음 사람이 또 밟을 것들

### 5-1. 씬 파일에 옛 HUD 가 **구워져 저장돼 있었다** (§5-1 지뢰의 실물)

`스마트월드_1.tscn` · `스마트월드_2.tscn` 안에 `HUD` CanvasLayer 와 라벨이
**노드로 저장돼 있다.** 예전 빌더가 owner 를 트리 전체에 박은 그 사고의 잔재다.

그래서 지금까지 **HUD 가 항상 두 벌**이었다. 씬에 구워진 쪽은 갱신이 안 되니
`"페인트 12 / 12 (회수대기 0)"` 이 화면에 굳어 있었고, 살아 있는 HUD 가 그 위에
같은 내용을 덧그려서 **아무도 눈치채지 못했다.** 글씨를 없애자마자 드러났다.

→ 씬 파일을 고치지 않고 `월드.gd` 가 런타임에 치운다.
  씬을 고치면 디자이너 편집본이 날아갈 위험이 있고, 이 사고는 또 날 수 있기 때문이다.
  ⚠ `queue_free()` 는 지연 삭제라 같은 이름으로 새 노드를 만들면 Godot 이 `HUD2` 로
  이름을 바꾼다. **노드를 재사용**해야 한다.

### 5-2. 새 스크립트의 `class_name` 은 헤드리스에서 아직 없는 이름이다

`class_name` 은 **에디터가 한 번 훑어야** 전역에 등록된다. 등록 전에 헤드리스 검사를
돌리면 `Identifier "페인트HUD" not declared` 로 **월드.gd 가 통째로 로드 실패**한다.
이번에 검사 3개(`test_사망판정` `test_낙하사망` `test_통로전환`)가 이 이유로 깨졌고,
증상은 "낙하감시가 안 붙었다" 처럼 **엉뚱한 곳**에서 나왔다.

→ 새 스크립트는 `class_name` 이 아니라 **경로 `preload` 상수**로 참조한다.
  `extends` 도 마찬가지 (`extends "res://..."`). 이 프로젝트가 원래 쓰던 방식이다.

### 5-3. 검사가 깨지면 **기준선부터 재라**

위 실패를 보고 "내가 뭘 깼나" 를 코드에서 찾으려 했는데, 먼저 `git stash` 로
손대기 전 상태를 재는 게 빨랐다(22/22 · 11/0 · 19/0). 그래야 "내가 깬 것"과
"원래 깨져 있던 것"이 갈린다.

### 5-4. `stage_1-1, 1-2` 에서 HUD 가 **한참 빈 화면**이었다 (제보 → 고침)

"이 씬에는 왜 HUD 를 안 붙였냐"는 제보가 왔다. 붙어 있었다 —
`페인트HUD` 노드가 트리에 있는 것도 확인했다. **그릴 게 없었을 뿐이다.**

- 이 시스템은 탄약이 없다 → 찬 점이 하나도 없다
- 회수줄에는 **완성된 플랫폼만** 들어간다
- 그런데 `stage_1-1` 의 플랫폼은 완성에 **11발**이 필요하다

→ **11발을 쏠 때까지 HUD 가 완전한 빈 화면**이었고, 당연히 "안 붙였다"로 읽혔다.
   스마트월드는 시작부터 찬 점 12개가 보여서 이 구멍이 안 드러났다.

**고침**: 어댑터에 `진행줄()` 을 추가해 **칠하는 중인 대상을 점선 칸**으로 먼저 보여준다.
이제 **첫 발부터 화면이 반응한다.** 점선 ↔ 빈 점을 알파가 아니라 **끊긴 선**으로 나눈 이유는
흑백 게임이라 밝기 차이만으로는 배경에 따라 구분이 무너지기 때문이다.

> 교훈: **"빈 상태에서 어떻게 보이나"를 반드시 따로 찍어 봐야 한다.**
> 채워진 상태만 확인하면 이 구멍이 안 보인다.

### 5-5. `수동_회수()` 는 발수를 조용히 버린다 (**이번에 안 고침**)

```gdscript
var 항목 := _회수줄.pop_front()      # 먼저 꺼내고
if not is_instance_valid(대상): continue   # ← 환급 없이 버려진다
if 대상.되돌리기(): ...                     # false 여도 버려진다
```

칠한 대상이 `queue_free` 되거나 `되돌리기()` 가 false 를 주면 그 발수가 **영구 증발**한다.
게다가 `while` 이라 **E 한 번에 여러 항목이 팝될 수 있다** — 앞의 둘을 조용히 버리고
셋째를 회수하고 끝난다. 플레이어에겐 "E 눌렀는데 엉뚱한 게 돌아오고 탄약도 덜 왔다"가 된다.

규칙이 바뀌는 수정이라 HUD 와 섞지 않았다. **HUD 는 이걸 숨기지 않는다** —
`남은 + 회수대기 + 잠김 < 최대` 가 되면 남는 칸을 흐린 빈 칸으로 그려
"페인트가 어디론가 없어졌다"가 화면에 보이게 했다.

## 8. 후속 — 타일맵 스테이지에도 탄약을 신설 (같은 날)

§5-4 를 고치고 나니 다음 질문이 왔다. "스마트월드처럼 좌상단에 탄약이 보이면 좋겠다."

### 왜 없었나

`tile_paint_map.gd` 에 탄약 개념이 **아예 없었다.** `proto_gun` 은 아무한테도 안 묻고 그냥 쐈다.
스마트월드 `총.gd` 와 비교하면 이 두 줄이 통째로 없었던 것이다.

```gdscript
if not 코어.쏠_수_있나(): return
코어.발사_소모()
```

### 숫자를 어떻게 정했나

`stage_1-1, 1-2` 를 실측했다.

| 항목 | 값 |
|---|---|
| 칠할 수 있는 플랫폼 | 103 개 |
| 전부 칠하는 데 드는 총 발수 | 440 발 |
| 가장 큰 플랫폼 하나 | **12 발** |

★E 로 회수하면 발이 돌아오므로 탄약은 "총 사용량 제한"이 아니라
**동시에 칠해둘 수 있는 양의 상한**이다. 그래서 12 이하로 두면 큰 플랫폼 하나도 못 칠한다.
→ **14 발**로 정했다(도형님 지시). `stage_lab.gd` 의 `타일_최대_탄약` 에서 언제든 늘릴 수 있다.

### 규칙은 `페인트_코어.gd` 를 그대로 따랐다

같은 게임인데 스테이지마다 자원 규칙이 다르면 플레이어가 두 번 배워야 한다.

| 상황 | 처리 |
|---|---|
| 발사 | 1발 차감 |
| 빗나감 / 이미 같은 색 / 못 칠하는 대상 | **그 자리에서 환급** |
| 회색화 | 원래 발 + 덮은 1발이 **함께 잠김** |
| E 회수 | 그 플랫폼에 든 발을 통째로 환급 |
| 사망 | 지형·탄약을 **함께** 되돌림 |

### 손댄 파일

| 파일 | 무엇을 |
|---|---|
| `tile_paint_map.gd` | `최대_탄약`(export) · `쏠_수_있나` · `발사_소모` · `빗나감` · `_탄약_정산` · `리셋` |
| `proto_gun.gd` | 쏘기 전에 탄약을 묻는다 (덕 타이핑) |
| `proto_bullet.gd` | 아무것도 못 맞히고 사라지면 `빗나감()` 통보 |
| `stage_lab.gd` | `타일_최대_탄약` export → 전달 · 사망 시 `리셋()` |
| `페인트_HUD_어댑터_타일.gd` | 진짜 탄약 값을 넘김 |

### ⚠ 여기서도 지뢰가 있었다

**(1) 공유 코드를 건드렸다.** `proto_gun` · `proto_bullet` 은 `zone_01/02/world_1` 의
`PaintSystem` 도 쓴다. 거기엔 탄약이 없다.
→ **덕 타이핑**(`has_method("쏠_수_있나")`)으로 갈랐다. 메서드가 없으면 예전처럼 그냥 쏜다.
`최대_탄약 = 0` 이면 무제한이라 예전 동작도 그대로 남는다.

**(2) 빗나간 총알이 조용히 사라지고 있었다.** `ProtoBullet` 은 수명이 다하면
`queue_free` 로 끝이었다. 탄약이 생긴 지금 그대로 두면 **허공에 쏠 때마다 손해**가 되어
"맞혀야만 잠긴다" 규칙이 깨진다. → `_소멸()` 로 모아 환급하게 했다.

**(3) 탄약만 채우면 무한 보급이 된다.** 처음엔 사망 시 `탄약_리셋()` 만 부르려 했는데,
그러면 칠해둔 지형은 남고 탄약만 14 로 돌아와 **죽을 때마다 페인트가 공짜로 생긴다.**
반대로 지형만 되돌리면 탄약이 말라 스테이지를 못 깬다. → `리셋()` 이 둘을 **같이** 한다.

### 검증

검사 13개 전부 통과(§6 과 동일). 화면 확인:
`탄약 4/14 · 진행 1 · 묶음 3발+3발 · 잠김 3` →
칸이 정확히 **4 + 1 + 3 + 3 + 3 = 14** 로 맞아떨어진다(합계 불변식 성립).

### 남은 것

- [ ] **14 발이 실제로 playable 한지는 플레이해 봐야 안다.** 이 스테이지는 원래
      "탄약 무제한"을 전제로 지형이 짜였다. 막히면 `stage_lab.gd` 의
      `타일_최대_탄약` 을 올리면 된다(코드 수정 불필요).
- [ ] 부분 색칠은 여전히 **E 로 회수 불가**다(완성돼야 큐에 들어간다).
      탄약이 생긴 지금은 이게 더 아프다 — 큰 플랫폼에 붓다가 모자라면 물릴 방법이 없다.
      §7 의 `_큐.append` 위치 문제와 같은 건이다. 기획 판단이 필요하다.

## 9. 후속 — 발사 순간의 깜빡임 제거 (같은 날)

도형님 제보: *"페인트가 날라가는 동안에는 1발이 차감되었다가 지형에 닿는 순간 또 바뀐다.
실시간으로 변하니까 정신사납다."*

### 무엇이 문제였나

탄약은 **쏘는 순간 깎이고**(선입금), 결과가 나와야 환급되거나 잠긴다.
그래서 HUD 가 `남은_탄약` 을 그대로 그리면 한 발에 **두 번** 바뀐다.

```
쏨 → 칸이 꺼짐 → (총알 비행 0.3~1초) → 착탄 → 다시 켜지거나 빈 칸이 됨
```

**빗나가면 꺼졌다 켜지기만 해서 깜빡임만 남는다.** 정보는 0인데 시선만 뺏긴다.

### 어떻게 고쳤나 — 규칙은 안 건드렸다

`_비행중`(날아가는 중인 발 수)을 세고, **HUD 는 `남은_탄약 + 비행중` 을 그린다.**

- 비행 중에는 화면이 **전혀 안 변한다**
- **착탄하는 순간 딱 한 번** 바뀐다 (칠해짐 → 빈 칸 / 빗나감 → 그대로 / 회색 → 빗금)

⚠ **`남은_탄약` 은 손대지 않았다.** `쏠_수_있나()` 도 그대로라 비행 중인 발로 또 쏠 수는 없다.
`비행중` 은 **표시 전용**이고, 규칙 판정에 쓰면 안 된다.

합계 불변식도 그대로다 — 비행 중인 발은 아직 어느 묶음에도 안 들어갔기 때문이다.

### 실제 동작 확인

```
시작            HUD=12 (실제 12, 비행 0)
발사 직후       HUD=12 (실제 11, 비행 1)   ← 안 변함 ✔
빗나가 착탄     HUD=12                     ← 끝까지 안 변함 ✔
다시 발사       HUD=12                     ← 안 변함 ✔
칠해져 착탄     HUD=11                     ← 여기서 처음 줄어듦 ✔
또 발사         HUD=11                     ← 안 변함 ✔
같은색이라 낭비 HUD=11                     ← 안 변함 ✔
```

### 손댄 곳

`페인트_코어.gd` · `tile_paint_map.gd` 에 `_비행중` + `비행중()`,
어댑터 둘의 `탄약()` 이 더해서 넘긴다. **두 시스템 모두 같은 방식**이다.

씬 전환·사망으로 총알이 결과를 못 알리고 사라질 수 있으므로
`리셋()` / `탄약_리셋()` 에서 `_비행중 = 0` 으로 턴다(안 그러면 있지도 않은 발이 계속 보인다).

### 남은 것

- [ ] 탄약이 진짜 0 인데 마지막 발이 날아가는 중이면, HUD 에 칸이 1 개 보이지만
      클릭해도 안 나간다(짧은 순간). 잘못된 표시는 아니지만 — **소리**가 붙으면
      "빈 총 소리"로 자연히 해결될 자리다(작업 D).
