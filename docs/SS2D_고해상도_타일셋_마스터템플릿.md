## 1. 머티리얼 구조 (재질이 바뀌어도 이건 그대로)

머티리얼 하나 = **엣지 메타 5개 + 필**.

| # | 이름 | `normal_range` | `texture_scale` | `z_index` | 텍스처 | taper |
|---|---|---|---|---|---|---|
| 1 | TOP | begin 45, distance 90 | 0.35 | 0 | `edge_top` | ✅ |
| 2 | LEFT | begin 135, distance 90 | 0.35 | 0 | `edge_left` | ✅ |
| 3 | BOTTOM | begin 225, distance 90 | 0.35 | 0 | `edge_bottom` | ✅ |
| 4 | RIGHT | begin 315, distance 90 | 0.35 | 0 | `edge_right` | ✅ |
| 5 | **CORNER** | begin 0, **distance 360** | 0.35 | **1** | `투명_256` (캐리어) | ❌ |

필: `fill_textures=[fill]`, `fill_texture_scale=0.35`, `fill_texture_z_index=-1`.

### 왜 이렇게 생겼는지 (다시 조사하지 말 것)

- **4방향만으로는 코너가 절대 안 생긴다.** SS2D 는 *한 엣지 안에서* 점이 꺾일 때만
  코너 쿼드를 만든다(`shape.gd edge_should_generate_corner`). 90° 모서리는 항상
  서로 다른 방향 엣지의 경계라 그 조건에 안 걸린다. 실측: 4방향만 → 코너 0개.
- 그래서 **5번째 전방향(0~360) 코너 전용 메타**를 얹는다. 이게 도형 전체를
  엣지 하나로 잡아서 모든 90° 지점에 코너 쿼드를 만든다. 실측: 사각 OUTER 4, L자 OUTER 5 + INNER 1.
- 코너 전용 메타의 `textures` 에 **투명 캐리어가 반드시 있어야 한다.** null 이면 코너도 안 생긴다.
- 캐리어가 **256×256** 인 이유: 코너 쿼드 크기는 엣지 텍스처의 **높이**가 정한다.
  256 × 0.35 = 90px = TOP 띠 두께 → **코너와 엣지 크기는 배율과 무관하게 자동으로 맞는다.**
- 코너 전용 메타에는 **taper 를 붙이지 않는다.** 0~360 은 닫힌 외곽선을 통째로 도는
  엣지라 `is_edge_contiguous` 가 true 이고, taper 는 `not is_edge_contiguous` 일 때만 걸린다.
- 코너 `z_index = 1` → 4방향 엣지 위에 그린다.
  ⚠ **`_edge_meta_materials` 의 배열 순서는 그리는 순서를 정하지 않는다. z_index 가 정한다.**
  (배열 순서만 바꿔 봤더니 결과가 완전히 동일했다)

## 2. 애드온 수정 이력 (이 두 건이 전부다)

`addons/rmsmartshape` 는 지금까지 **P0 4파일 / P1 1파일** 만 고쳤다.

### P0 — 해상도와 월드 크기 분리 (2026-08-24, 커밋 aab4b63)

| 파일 | 변경 |
|---|---|
| `materials/edge_material.gd` | `texture_scale: float = 1.0` export 추가 |
| `shapes/quad.gd` | `texture_scale` 필드 + duplicate/matches_quad 반영 |
| `shapes/shape.gd` | `c_scale = edge_material.texture_scale` 연결 |
| `shapes/edge.gd` | UV 주기에 배율 반영 + `maxf(1.0, roundf(...))` 하한 |

원래 SS2D 는 "텍스처 1px = 월드 1px" 로 굳어 있어서 고해상도 일러스트를 쓰면
지형이 물리적으로 커져 버렸다. 또 엣지가 주기의 절반보다 짧으면 reps 가 0 이 되어
UV 가 한 줄로 붕괴했다.

### P1 — taper 를 배율에 맞추고 곡선 안전장치 (이번 작업)

`shapes/shape.gd` **1파일 2군데** (`_taper_quad`):

```gdscript
# P1-1 (taper 길이)
- var offset: Vector2 = delta_normal * taper_size
- var fit: bool = absf(taper_size.x) <= quad.get_length_average()
+ var taper_length: float = taper_size.x * quad.texture_scale
+ var fit: bool = taper_length <= quad.get_length_average()
+ var offset: Vector2 = delta_normal * taper_length

# P1-2 (fit 실패 시)
- else:
-     quad.is_tapered = true
-     quad.texture = taper_texture     # 쿼드 전체를 taper 로 갈아끼움
+ (분기 자체를 삭제 — taper 를 그냥 건너뛴다)
```

**왜 필요했나**

- `delta_normal * taper_size` 는 Vector2 **성분곱**이라
  가로 엣지는 `taper_size.x`, 세로 엣지는 `taper_size.y` 가 길이가 됐다.
  정사각 텍스처로만 쓸 수 있었고, 그러면 단면 해상도가 길이에 묶인다.
- `texture_scale` 이 안 곱해져 **텍스처 1px = 월드 1px** 로 굳어 있었다.
  배율 0.35 의 타일셋에서 taper 만 해상도가 1/2.86 로 떨어져
  곡선에서 늘어난 자국으로 보였다.
- fit 실패 시 쿼드 **전체**를 taper 로 덮으면, 곡선의 짧은 끝쿼드 하나가
  통째로 늘어난 검은 슬래브가 되어 실루엣 밖으로 튀어나왔다.

**하위호환 — 바이트 단위로 증명함**

저장소의 SS2D 머티리얼 **16개 × 도형 8종 = 128 조합**의 정점을 덤프해
수정 전/후를 비교:

```
수정 전 SHA256 7887DB62338A7F25922084C8F97E0F41A76CEF9A5937FD02058062BD78031F61
수정 후 SHA256 7887DB62338A7F25922084C8F97E0F41A76CEF9A5937FD02058062BD78031F61  → 동일
```

이유: `_taper_quad()` 는 `use_taper_texture` 가 true 이고 taper 텍스처가 실제로
있을 때만 그 두 줄에 도달한다. 저장소의 기존 머티리얼은 **전부
`use_taper_texture = false` 이고 taper 텍스처를 가진 것이 하나도 없다.**

재현: `Godot --headless --path . -s res://tools/검증_taper_하위호환.gd`

## 3. 텍스처 규격

### 3-1. 손으로(또는 AI로) 만드는 원본 — 테마당 **4장뿐**

| 원본 | 크기 | 용도 |
|---|---|---|
| `<재질>_top` | 1024 × 256 | TOP 엣지 |
| `<재질>_bottom` | 1024 × 192 | BOTTOM 엣지 |
| `<재질>_side` | 1024 × 256 | LEFT (+ 좌우반전해서 RIGHT) |
| `<재질>_fill` | 1024 × 1024 | FILL detail |

**검정 테마만 만든다.** 흰색은 전부 파생된다.

### 3-2. 파생되는 것 — 나머지 28장 전부

| 파생물 | 개수/테마 | 만드는 법 |
|---|---|---|
| `edge_left` / `edge_right` | 2 | side 원본 + 좌우반전 |
| `corner_outer` / `corner_inner` | 2 | **엣지 단면에서 극좌표 합성** (§4) |
| `fill_solid` | 1 | fill_detail 을 순환 블러 + 대비 20% 압축 |
| `taper_*_{left,right}` | 8 | 엣지의 u∈[0.31−N/1024, 0.31] 구간 + 알파 페이드 |
| WHITE 테마 전체 | 16 | **BLACK 의 휘도 반전** (알파 그대로) |

> ★ **코너는 AI로 따로 그리지 않는다.** 그리면 단면이 절대 안 맞는다.
> 엣지에서 합성해야 edge↔corner 연속성이 수식으로 보장된다.

### 3-3. import 정책 (프로젝트 규약)

```
compress/mode = 0      (무손실)
mipmaps/generate = false
```
새 PNG 를 만든 뒤에는 반드시 `Godot --headless --path . --import` 를 한 번 돌린다.
`-s` 실행만으로는 새 파일이 import 되지 않아 `load()` 가 null 을 돌려준다.

## 4. 코너 합성 규칙 (재질이 바뀌어도 동일)

코너는 엣지를 **극좌표로 감아서** 만든다.

- **OUTER**: 중심 UV(0,1) = 지형 안쪽 구석, `v = 1 − r/S`
- **INNER**: 중심 UV(1,0) = 바깥 빈 구석, `v = r/S`
- `u` 는 반드시 **호 길이**에 비례. 각도에 비례시키면 방사형으로 뭉갠다.
- 각도 블렌드에 smoothstep → 이음매에서 반대쪽 텍스처가 안 섞인다.
- 경계열은 `u = 0.31` 의 TOP 단면, 아래 행은 `u = 0.62` 의 SIDE 단면(역방향).

**UV 방향** (진단 텍스처로 픽셀 실측한 값, 추측 아님):
OUTER·INNER 모두 **UV(1,0) = 지형 바깥, UV(0,1) = 지형 안쪽**. 회전 0 = 우상 코너.

**검증**: 합성 수식을 다시 계산해 커밋된 PNG 와 비교하면 **최대 잔차 1.00/255**
(= 8비트 반올림). `tools/측정_grass_v4_품질.gd` 의 [5-b] 항목.

## 5. taper 규격

| 항목 | 값 | 근거 |
|---|---|---|
| 크기 | **128 × 256** | 폭 128 × 배율 0.35 = 월드 44.8px = 코너 반너비 |
| 월드 길이 | 44.8px | 띠가 코너 자리 직전에서 사라진다 |
| 내용 | 엣지의 `u ∈ [0.31 − 128/1024, 0.31]` 실제 그림 | 바깥 끝이 코너 경계열과 일치 |
| 알파 | 바깥 **35%** 구간에서 코사인 페이드 → 0 | 띠가 뚝 끊기지 않는다 |
| 붙이는 곳 | 4방향 엣지만 (`textures_taper_left/right`) | 코너 전용은 contiguous 라 안 걸린다 |

### 만들 때 틀리기 쉬운 것

- **평균 단면으로 만들면 안 된다.** 톤은 완벽하게 이어지지만 그림이 사라져
  뭉갠 자국이 된다. 열평균 단차는 PASS 인데 화면은 더 나쁘다 (실제로 겪음).
- taper 의 u 폭은 그냥 `N / 엣지폭` 이다. 배율이 약분되므로 배율을 알 필요가 없다.
- 텍스처 폭이 곧 월드 길이 × (1/배율) 이다. 폭을 키우면 taper 가 길어진다.

## 7. 제작 파이프라인 (재질 하나 기준)

```

  ↓ grayscale normalization
  ↓ seamless processing    ★ 순환이어야 한다. 3×3 으로 깔고 가운데를 잘라낸다

  ↓ 안쪽 알파 페이드         띠 안쪽 22% 코사인 → 필로 녹아든다
  ↓ FILL generation        detail(원본+감마+엣지 안쪽 톤 맞추기) → solid(순환블러+대비20%)
  ↓ CORNER synthesis       ★ 엣지 단면에서 극좌표 합성 (§4) — AI 로 그리지 않는다
  ↓ TAPER synthesis        엣지 u∈[0.31−N/1024, 0.31] + 알파 페이드 (§5)
  ↓ WHITE variant          BLACK 휘도 반전 (알파 그대로)
  ↓ import                 compress 0 / mipmap off → --import 한 번
  ↓ MATERIAL               tools/생성_SS2D_타일셋_머티리얼.gd  (구조는 손대지 않는다)
  ↓ STRESS TEST            tools/검증_taper_9도형.gd → 9도형 렌더
  ↓ 수치 검증               tools/측정_실루엣_단차.gd / 측정_grass_v4_품질.gd
  ↓ VISUAL INSPECTION      줌 0.82 (실제 플레이 거리) + 줌 3.0 (확대)
```

## 9. 새 타일셋 하나를 만드는 순서

1. **원본 4장 준비** (검정 테마): top 1024×256 / bottom 1024×192 / side 1024×256 / fill 1024×1024
2. **폴더 생성**: `assets/textures/smartshape/<재질>_v1/{black,white}/`
3. **파생 굽기**: 감마 1.60 → 엣지 4장 → 필 2장 → 코너 2장 → 흰색 16장
   (`tools/grass_v4_pipeline/apply_final.py` 를 재질별로 복사해 경로만 바꾼다.
    ⚠ 이 PC 에는 파이썬이 없다 — 파이썬이 있는 PC 에서 굽거나 GDScript 로 옮긴다)
4. **taper 굽기**: `생성_grass_v4_taper.gd` 를 `--길이=128 --높이=256 --방식=slicefade --페이드=0.35`
5. **import**: `Godot --headless --path . --import`, `.import` 를 compress 0 / mipmap off 로 맞춤
6. **머티리얼**: `생성_SS2D_타일셋_머티리얼.gd --재질=<재질> --폴더=<폴더>`
   (먼저 `--확인만` 으로 빠진 PNG 목록을 확인한다)
7. **스트레스 씬**: `검증_taper_9도형.gd`
8. **수치 검증**: `측정_실루엣_단차.gd` (< 6/255) + `측정_grass_v4_품질.gd`
9. **눈으로 확인**: 줌 0.82 / 3.0
10. **회귀**: `docs/다음작업_프롬프트.md §1` 의 검사 + `test_ss2d_해상도분리`

## 9-B. 재질별 파라미터 (BRICK 을 만들며 발견 · 2026-08-24 추가)

grass 하나만으로는 안 보이던 것들이다. 새 재질마다 **측정해서** 정한다.

| 파라미터 | grass_v4 | brick_v1 | 정하는 법 |
|---|---|---|---|
| `--감마` | 1.60 | **2.80** | §6 사다리를 재질 원본으로 다시 뽑아 BLACK 평균이 **31 근처**가 되는 값 |
| `--코너방식` | `polar` | `miter` | 유기적 질감이면 polar, **규칙적 격자**(벽돌·타일)면 miter |
| `--코너알파폭` | (안 씀) | **0.16** | miter 코너의 후광 제거. 아래 9-C 참고 |
| 띠 기준선 | (동일) | (동일) | ★ 최고점이 아니라 **열별 실루엣의 중앙값** |

> ※ 2026-08-25 재측정으로 감마가 바뀌었다 — **brick 2.62 / sewer 2.05 / wood 2.35**.
>   위 표의 2.80 은 BRICK 첫 굽기 때 값이다. 목표는 늘 **BLACK 평균 31 근처**다.

### 왜 감마가 재질마다 다른가
감마는 원본의 밝기 분포에 작용한다. grass 원본은 평균 70 이라 1.60 이면 31 이 되지만,
brick 원본은 평균 ~140 이라 1.60 으로는 **76** 밖에 안 내려간다.
**BLACK 평균 31 / WHITE 224 라는 목표를 맞추는 것**이지 감마 숫자를 맞추는 게 아니다.
(brick 은 2.80 에서 BLACK 32.0 / WHITE 223.0 이 되어 grass 와 같은 검정으로 읽힌다.)

내부 디테일 단계는 재질마다 달라도 된다 — grass 12단계, brick 45~60단계.
벽돌은 줄눈 구조가 읽혀야 하므로 오히려 더 넓어야 한다.

### 왜 코너 방식이 재질마다 다른가
`polar` 는 띠를 코너에 **감는다**. 잔디처럼 방향성이 없는 질감은 감아도 티가 안 나지만,
벽돌 줄눈은 부채꼴로 휘어져서 직선 줄눈과 절대 안 맞는다.
`miter` 는 두 띠를 직선 그대로 두고 45도에서 섞는다.
※ 실측상 두 방식의 이음매 수치는 거의 같았다(18.0 vs 17.6). **miter 를 고르는 이유는 수치가 아니라
   줄눈이 직선으로 남는다는 것**이다.

### ★ 띠 기준선은 중앙값으로 (이게 제일 크게 먹혔다)
띠를 자를 때 기준을 '가장 뾰족한 봉우리' 로 잡으면,
골이 깊은 재질은 띠의 대부분이 빈 공간이 된다.
brick 에서 엣지가 **40.7% 투명**(잔디 21.5%)이 되었고,
그 빈 구간을 코너 합성이 코너 전체로 퍼뜨려 **반투명한 유령 블록**으로 렌더됐다.

중앙값으로 바꾼 뒤: 엣지 투명 40.7% → **25.8%**, 코너 불투명 20.7% → **39.2%**,
오목 코너 이음매 **29.9 → 9.4 / 255**.

### ★ 합격 기준은 절대값이 아니라 **그 재질의 대조군 대비**
`< 6/255` 는 grass 기준으로 잡은 값인데, 재질마다 바탕 대비가 다르다.

| | 대조군(직선) | 볼록 | 오목 |
|---|---|---|---|
| grass_v4 | 2.77 | 6.90 (2.5배) | 6.14 (2.2배) |
| brick_v1 | **6.86** | 15.83 (2.3배) | 9.42 (1.4배) |

벽돌은 줄눈 때문에 **직선 구간에서도** 6.86 이 나온다. 그러니 절대값 6 을 요구할 수 없다.
→ **판정은 "그 재질의 대조군 대비 2.5배 이하"** 로 본다.

### ⚠ 측정 도구의 함정 (같은 함정에 세 번 빠졌다)
1. 열 평균에 **배경을 포함하면 안 된다.** 볼록 코너 바깥은 지형 면적 자체가 줄어서
   '도형이 끝난 것' 을 이음매로 오인한다. 벽돌에서 20~35/255 의 가짜 값이 나왔다.
   → 양쪽 열 **모두 지형인 행만** 평균한다.
2. 밝기 통계를 **알파>127 로 필터하면** 낮은 알파의 이상 픽셀을 놓친다.
3. 눈으로 "밝은 블록" 이라고 판단하기 전에 **픽셀값을 찍어 봐라.**
   벽돌 코너의 '밝은 사각형' 은 실제로는 배경(0.659)보다 **어두운** 0.50~0.65 였다.
   검은 지형 옆이라 밝아 보였을 뿐이고, 원인은 밝은 색이 아니라 **알파 부족**이었다.

## 9-C. 코너 후광(ghost)과 코너 UV — 2026-08-25 에 실측으로 잡은 두 가지

BRICK/SEWER/WOOD 를 확대하면 코너 둘레에 옅은 반투명 잔상이 남았다.
원인을 추측하지 않고 알파를 직접 센 결과 **서로 다른 두 가지**였다.

### (1) 엣지 안쪽 알파 페이드가 뒤집혀 있었다 (진짜 버그)

`_엣지마감()` 의 마스크가 `0.5*(1+cos(PI*(1-t)))` 였다. 이건
**가장 안쪽 행에서 1, 페이드 시작 지점에서 0** 이다 — 의도와 정반대다.

실측(1024x256 엣지의 안쪽 행 알파):

```
grass_v4 (파이썬으로 구움 · 의도한 모양)  … 251 → 서서히 → y=253 에서 0
brick/sewer/wood (GDScript)             … 255 → y=200 에서 **0** → 다시 → y=255 에서 **255**
```

즉 지형 안쪽 78% 지점에 **완전히 투명한 가로줄**이 생기고 맨 안쪽 행은 불투명이었다.
그 투명한 줄이 코너 합성에서 apex 둘레 고리로 감겨 유령 실루엣이 되었고,
실제 렌더에서는 지형 내부에 **옅은 사각 테두리**로도 보였다.

→ `0.5*(1 - cos(PI * d/n))` 으로 고쳤다. `d` 는 안쪽 끝에서 잰 거리다.

### (2) miter 코너의 각도 블렌드가 너무 넓었다

miter 는 45도 대각선에서 TOP/SIDE 두 띠를 섞는데, 블렌드 폭이 90도의 70%
(= 45도 ±31.5도) 였다. 그래서 **SIDE 실루엣 바깥**인 지점에서도 TOP 이 26% 섞이고,
TOP 은 그 깊이에서 불투명이라 **알파 60짜리 반투명 덩어리**가 실루엣 밖에 얹혔다.

색은 넓게 섞어야 이음매가 안 보이고, 알파는 좁게 끊어야 실루엣이 산다.
그래서 `--코너알파폭` 으로 **알파에만 좁은 폭**을 쓴다 (색은 기존 0.70 그대로).

| 코너 OUTER · 실루엣 밖 잔여 알파 | 수정 전 | `--코너알파폭=0.16` |
|---|---|---|
| brick | 13.82% | **2.04%** |
| sewer | 21.85% | **2.41%** |
| wood  | 35.53% | **7.03%** |

실제 렌더(5배 확대 · 밝은 배경)에서 **반투명 픽셀 4.14% → 2.26%**.
참고로 승인된 grass_v4 는 같은 측정에서 5.88% 다 — 잔디는 원래 부드러운 실루엣이라
이 수치 자체가 품질 기준은 아니고, **같은 재질의 수정 전/후 비교**로만 쓴다.

### (3) 덤으로 잡힌 것 — 512 코너가 그림을 가로로 2배 압축하고 있었다

코너 쿼드의 **월드 크기**는 캐리어(`투명_256`) × 배율 = 89.6px 로 고정인데,
u 매핑이 `float(코너변)` 을 그대로 써서 코너크기 512 에서는
엣지 그림 **179 월드px 분량**을 89.6px 에 밀어 넣고 있었다.
→ 코너에서만 벽돌이 좁아지고 코너 쿼드 경계가 **사각 자국**으로 드러났다(하수에서 특히).

u 길이는 텍셀 수가 아니라 월드 길이로 재야 한다 → `코너캐리어(256)` 기준으로 고쳤다.
고친 뒤에는 **코너크기 256 과 512 의 렌더가 구분이 안 된다**(512 는 단순 업샘플).
512 를 유지한 것은 확정값이기 때문이고, 파일 크기 외에 이득은 없다.

⚠ 이 수정은 `polar` 경로에도 들어갔다. grass_v4 는 다시 굽지 않으므로 영향이 없지만,
   나중에 `grass_v5` 를 구우면 v4 와 코너가 달라진다는 뜻이다.

## 12. 지뢰밭 (전부 실제로 한 번씩 터진 것)

1. **비교 렌더는 모든 도형이 같은 배경 위에 있어야 한다.** 일부가 배경 밖으로 나가면
   반투명한 술이 다른 색과 섞여 수치가 통째로 뒤집힌다. 배경 크기는 계산해서 넣을 것.
2. **`_edge_meta_materials` 배열 순서 ≠ 그리는 순서.** z_index 가 정한다.
3. **정규화 자기상관·연속길이 지표는 붓질에 오염된다.** 열 평균을 써야 분해능이 생긴다.
4. **열평균 단차만 믿으면 "뭉갠 것"을 놓친다.** 고주파 에너지를 같이 봐야 한다.
5. **`force_update()` 는 노드가 트리에 없으면 아무것도 안 한다.** 메시가 조용히 0개가 된다.
6. **`shape_closed.gd` 는 deprecated.** `SS2D_Shape` + `add_points()` → `close_shape()`.
7. **PIL 블러/리사이즈는 순환하지 않는다.** 3×3 으로 깔고 가운데를 잘라야 한다.
8. **새 PNG 는 `--import` 를 한 번 돌려야 `load()` 가 된다.**
9. **`ResourceSaver.save()` 로 .tres 를 다시 쓰면 `uid://` 가 사라진다.**
   uid 로 참조하는 곳이 있으면 1행을 복구해 줄 것.
10. **베이크된 테스트 씬은 머티리얼을 바꿔도 갱신되지 않는다.**
    `.tscn` 안에 메시가 sub_resource 로 저장돼 있다. 해당 `build_*.gd` 를 다시 돌려야 한다.
11. **PowerShell 로 Godot 에 한글 인자를 넘기면 깨진다.** Bash 로 실행할 것.
12. `c_extends`(shape.gd) 는 아직 **리터럴 0.0 으로 죽어 있는 손잡이**다. 지금은 쓸 일이 없다.
