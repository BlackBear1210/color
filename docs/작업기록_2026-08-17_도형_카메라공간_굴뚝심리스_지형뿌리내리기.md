## 3. 카메라 — 왜 "층" 을 하나 더 두었나 (핵심 설계)

카메라 값을 정하는 주인이 이미 세 개였다.

```
월드.gd          씬 시작에 한 번          리밋 · 줌
카메라_연출.gd    ★매 물리 프레임          리밋 · 줌 · 시선   ← 이게 다 덮어쓴다
장면전환/등장연출  전환할 때                줌 트윈
```

그래서 "굴뚝에 들어가면 조인다" 를 그냥 얹으면 다음 프레임에 지워진다.
**실제로 `장면전환.gd` 의 줌 트윈은 구역 연출이 붙은 씬에서 첫 프레임에 지워져
아무 일도 하지 않고 있었다** — 화면상 그냥 "연출이 약하다" 로만 보여서 아무도 몰랐다.

→ 곱셈으로 분리했다.

```
zoom = 기준 줌(월드/구역) × 공간 혼합(굴뚝) × 연출 배수(짜잔)
리밋 = lerp(기준 리밋, 공간 리밋, smoothstep(혼합))
시선 = lerp(구역 시선, 공간 시선, 혼합)
```

트윈하는 값은 **`_공간_혼합` 0~1 하나뿐이다.** 기준값이 매 프레임 바뀌어도 싸우지 않는다.

### 왜 여기서는 시간 트윈인가

`카메라_연출.gd` 는 "전환은 시간이 아니라 위치로 굴린다" 를 못박아 둔 파일이다
(Vane 2019 혹평의 원인). 카메라 공간은 그 규칙을 **일부러 어긴다**:

- x 구역 전환은 **경계 없는 연속 이동** → 위치 보간이 맞다
- 굴뚝 진입은 **문을 지나는 이산 사건**(Area2D 1회) → 진행도 축이 하나로 정해지지 않는다
  (아래로도, 옆으로도 들어올 수 있다) → 시간 트윈이 맞다

대신 Vane 식 실패는 두 가지로 막았다.
① 되돌아 나오면 **즉시 반대로** 트윈한다 ② 트윈 시간을 **남은 거리에 비례**해 줄인다.

### 굴뚝 안에서 화면이 벽 밖으로 안 새는 원리

`ProtoCamera._clamp_to_limits` 는 **리밋이 화면보다 좁으면 카메라를 리밋 중앙에 못박는다.**
굴뚝 안쪽은 306px, 화면은 1747px(줌 1.10) 이므로 카메라 x 가 굴뚝 중심에 고정된다.
자동 검사에서 좌우로 흔들었을 때 카메라 이동량은 **0.0000px** 이었다.

⚠ 다만 "화면에 벽 바깥이 안 보인다" 와 "카메라가 안 흐른다" 는 다른 이야기다.
화면 폭 1747px 중 굴뚝은 306px 이므로 나머지는 **지형이 채워야** 한다.
스마트월드_4 는 굴뚝 좌우가 이미 암반이라 저절로 해결됐다. 새로 굴뚝을 팔 때는
**암반 매스가 이미 있는 자리에 파야 한다** — 자세한 근거는 가이드 §5.

## 4. ★찾아서 고친 버그 — 전환 줌이 기획과 정반대로 동작했다

`장면전환.gd` 에는 이렇게 적혀 있었다.

```gdscript
## 통로로 들어갈 때 카메라가 이만큼 줌 인한다 (1 = 그대로).
const 들어갈때_줌: float = 0.94
```

**Godot 4 의 `Camera2D.zoom` 은 클수록 확대(줌 인)다** (Godot 3 과 반대다.
이 프로젝트도 `카메라_구역.gd` 에 "작을수록 넓게 보인다" 고 적어 두었다).
즉 0.94 는 **줌 아웃**이다. 주석과 정반대로 동작하고 있었다.

더 나쁜 건 테스트였다.

```gdscript
확인("들어갈 때는 줌 인(<1)", 장면전환.들어갈때_줌 < 1.0)   # ← 틀린 기준
```

**테스트가 코드와 같은 오해를 공유하면 검사가 있어도 아무것도 못 잡는다.**
2026-08-08 지뢰밭 §5-8("테스트가 실패하면 코드부터 의심하지 말 것")의 반대 사례로 기록해 둔다.

→ 수정: `들어갈때_줌 = 1.07`(실제로 조여든다) · 테스트 기준을 바로잡고
"나올 때가 들어갈 때보다 커야 한다" 검사를 추가했다(46 → 47개).

### 세 가지 뿌리

| 상황 | 만드는 것 | 모양 |
|---|---|---|
| 아래에 지면이 있다 | **기둥** | 발판 폭의 55%. 아래로 갈수록 넓어진다(무게가 흐르는 방향) |
| 옆 260px 안에 **큰** 덩어리가 있다 | **버팀대(코벨)** | 벽쪽이 두껍고 발판 끝이 얇다 = 벽에서 자라난 선반 |
| 아래도 옆도 허공이다 | **덩어리 꼬리** | 발판 폭 그대로 시작해 아래로 좁아진다 = 떠 있는 암반 덩어리 |

- 버팀대에 "**큰** 덩어리" 조건이 붙은 이유: 없으면 **선반과 선반을 서로 이어버린다.**
  갱도의 좌우 엇갈린 선반은 260px 간격이라 서로 사정거리 안에 있는데,
  그걸 이으면 있지도 않은 다리가 생긴다. → 상대 높이 300px 이상만 벽으로 인정한다.
- 꼬리 실루엣은 한 변을 **4단으로 나눠 단마다 흔든다.** 2단(직선)으로 만든 첫 시도는
  전부 똑같은 사다리꼴로 보였다(스크린샷으로 확인). 씨앗은 중심 x 좌표라 멱등하다.

### ★받침에 콜리전을 주지 않은 이유 (중요한 판단)

기둥을 단단하게 만들면 **레벨 통행성이 바뀐다.** 발판 아래 통로가 막히거나
의도치 않은 지름길이 생긴다. 스마트월드_1·2 는 이미 도달률이 낮은 상태라
(86중 11 · 44중 19 — 인수인계 문서 작업 A) 여기서 물리를 건드리면
**원인이 섞여 아무것도 판단할 수 없게 된다.**

→ 기본은 **그림만** 있는 배경 덩어리(z_index −2, 콜리전 없음).
발판은 "덩어리에서 자란 선반" 으로 보이지만 물리는 1px 도 안 바뀐다.
레벨검사로 확인했다 — 도달률이 **작업 전과 완전히 동일**하다(§6).

단단하게 원하면 `--콜리전` 을 붙인다. 그 뒤에는 반드시 레벨검사를 다시 돌려야 한다.
