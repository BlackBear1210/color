## 1. 디자이너 에셋 실측 & 파이프라인

### 1-1. 타일셋 PNG 5장은 "32px 타일"이 아니었다

GitHub Desktop 으로 올라온 `assets/tileset/*.png` 를 PIL 알파 바운딩박스로 실측한 결과:

| 파일 | 해상도 | 셀 배치 (384px 격자) | 내용 |
|---|---|---|---|
| `brick.png` | 768×768 | 2×2 | 상행 = 평면 벽돌 흑/백, 하행 = 액자형 벽돌 흑/백 |
| `wood.png` | 768×768 | 2×2 | 좌열 = 액자형, 우열 = 평면 / 상행 흑, 하행 백 |
| `rock.png` | 768×384 | 2×1 | 흑 / 백 (균열 무늬) |
| `soil.png` | 768×384 | 2×1 | 흑 / 백 (흙 알갱이 가장자리) |
| `grass.png` | 768×896 | 2×2 (우하단 비어있음) | 상행 = 풀 가장자리 흑/백, 좌하 = 두꺼운 흑 |

**한 칸이 384×384 이고, 그 안에서 실제 그림은 약 350×350**(바깥 ~17px 는 투명 여백).
가장자리는 유기적으로 뜯겨 있다(풀·돌 부스러기·벽돌 테두리).

→ **결론: 이건 타일맵 아틀라스가 아니라 "플랫폼 한 덩어리" 아트다.**
32px 셀로 잘라 쓰면 뜯긴 가장자리가 타일마다 반복돼 격자무늬가 보인다.
그래서 v3 는 **플랫폼 1개 = 스프라이트 1장**으로 쓰고, 크기 차이는 **9슬라이스 셰이더**가 흡수한다.

배치·경로는 전부 `scripts/proto/tile_art.gd` 의 `CATALOG` 한 곳에 있다.
**아트를 교체할 땐 같은 파일명으로 덮어쓰기만 하면 코드는 손댈 필요 없다.**

### 1-2. 캐릭터 Shoot 시트

`assets/player(shoot)/Shoot(black|white).png` = 3840×640 = **640px 6칸 중 5칸 사용**(6번째는 빈 칸).

- `assets/player(shoot)/shoot_frames.tres` 신규 생성 (black_shoot / white_shoot, 5프레임, 14fps)

## 2. 페인트 시스템 v3 — 플랫폼 단위 색칠

### 2-1. 왜 v2(타일맵 셀 단위)로는 안 되는가

7/24 회의 결정: **"플랫폼·장애물마다 최대 색칠 횟수가 있다. 8칸짜리 플랫폼은 4번 칠하면 전체가 바뀐다."**

v2(`paint_system.gd`)는 **타일 1칸이 색칠 단위**였다. 8칸 플랫폼은 8개의 독립된 칸이라
"4번 칠하면 전체" 라는 개념 자체가 성립하지 않는다. 색칠 단위를 **플랫폼 1개**로 승격해야 한다.

### 2-2. 셰이더 vs 다른 방법 — 결론은 "역할 분담"

| 층 | 담당 | 왜 |
|---|---|---|
| **규칙·판정** (몇 번 맞았나 / 지금 무슨 색인가 / 밟으면 죽나) | **CPU** — `scripts/proto/paint_platform.gd` | 퍼즐 게임은 판정이 결정론적이어야 하고, 저장·되돌리기·자동테스트가 가능해야 한다. GPU 픽셀을 되읽어 판정하면 느리고 비결정적이다 |
| **표현** (어떻게 퍼져 보이나) | **셰이더** — `shaders/ink_spread.gdshader` | "칠해진 면쪽으로 색이 퍼진다"는 게 정확히 셰이더 마스크의 일 |
| **연출** (튀는 물감·흐름·화면 흔들림) | **노드** — `scripts/proto/paint_fx.gd`, `paint_drip.gd` | 파티클/폴리곤이 잘하는 일 |

이 분리 덕분에 **아트·연출을 통째로 바꿔도 게임 규칙은 한 줄도 안 바뀐다.**
(zone_04 ↔ zone_05 가 규칙이 완전히 같은 이유가 이것이다)

### 2-3. 잉크 번짐 (Ink Spread Shader)

```
명중 → 그 지점의 로컬 UV 를 "씨앗(seed)" 으로 배열에 추가
     → 씨앗마다 반지름을 CPU 가 부드럽게 키움 (지수 감쇠 보간)
     → 셰이더: 픽셀 → 가장 가까운 씨앗까지의 거리 - 반지름
     → 그 값을 fbm 노이즈로 흔든다 = 원이 아니라 "번진 잉크"
     → 경계 근처에 "젖은 광택" 띠 (명중 후 0.8초에 걸쳐 마름)
```

- **번짐 애니메이션을 GPU `TIME` 이 아니라 CPU 에서 굴리는 이유**:
  저장/되돌리기/자동테스트에서 "지금 몇 % 번졌는가"를 정확히 알아야 하고,
  히트스톱(시간 정지)과도 맞물려야 하기 때문.
- 반지름 목표값은 **면적 비례**(원 넓이 = 진행률 × 플랫폼 넓이)로 시작해,
  진행률이 뒤로 갈수록 `pow(진행, 5.0)` 만큼 전체 반지름 쪽으로 가속한다.
  → **마지막 한 발에서 확 덮이는** 쾌감을 남기기 위한 튜닝. (§6-3 참조)
- **무색(아직 안 칠함) 상태 = 백 텍스처의 명암을 유지한 채 명도만 55%** 로 내린 것.
  (레벨디자인 가이드 §5 "회색(죽은 지형) 45~55%" 규격과 일치)

### 2-4. 최대 색칠 횟수 (내구도) 자동 계산

```
필요횟수 = ceil( 긴 변의 칸 수 / 2 ),  최소 1
```

| 플랫폼 | 필요 횟수 |
|---|---|
| 2칸 | 1 |
| 4칸 | 2 |
| **8칸** | **4** ← 회의에서 정한 예시와 일치 |
| 12칸 | 6 |
| 세로 9칸 기둥 | 5 |

개별 조정이 필요하면 인스펙터의 `필요횟수_수동` 에 값을 넣으면 그게 우선한다.

### 2-5. 9슬라이스 — 384px 덩어리 아트를 임의 크기 플랫폼에 붙이기

유기적인 테두리는 그대로 두고 가운데만 **원본 픽셀 비율에 가깝게 반복**한다.
덕분에 2칸짜리 발판이든 60칸짜리 바닥이든 무늬가 늘어나지 않는다.

## 3. ★가장 중요한 발견 — "왜 칠하는가"가 비어 있었다

작업 중 문서 2건이 **정면으로 반대**인 것을 발견했다.

| 문서 | 무색(칠 가능) 발판에 대한 서술 |
|---|---|
| `docs/레벨디자인_가이드.md` §3 부품표 **V1** | **"무색 발판 = 칠해야만 밟을 수 있음"** |
| `docs/기획서_규칙_플로우차트.md` 1-5 | "무색(칠 가능) 발판 = **안전**" |

그리고 **구현(`zone_lab.gd`)은 후자를 따르고 있었다.**

### 문제

무색이 이미 안전하다면 **굳이 물감을 쓸 이유가 없다.**
- 회의에서 정한 "최대 색칠 횟수"도 의미를 잃는다(제한할 자원이 애초에 쓰이지 않으니까).
- E 회수도 "칠한 길을 되돌리는 도구"라고 문서에 적혀 있지만, 칠할 필요가 없으면 되돌릴 것도 없다.
- 도형님이 말한 **"색을 칠하며 장애물을 피해 스테이지를 클리어하는 퍼즐적 희열감"** 이 성립하지 않는다.

### 조치

레벨디자인 가이드(V1) 쪽을 코드로 구현하되, **끌 수 있는 옵션**으로 두었다.

`PaintPlatform.무색일때_통과` (기본 **true**)
- `true` — **유령 지형**. 안 칠하면 통과해서 떨어진다. 칠하면 실체가 된다. → **칠할 이유**
- `false` — 기존 규칙. 무색이어도 밟을 수 있는 안전한 징검다리

구현: 유령 상태에서는 물리 레이어를 **4번(비트 8)** 으로 옮긴다.
→ 플레이어(mask=1)는 통과 · 총알(mask=1|8)은 명중 · 조준 궤적(전 레이어)은 표시.
**팀 파일(player.gd / Player.tscn / project.godot)은 한 줄도 안 고쳤다.**

이렇게 하니 E 회수도 비로소 뜻이 생긴다 — **칠해서 만든 길을 지워 아래를 여는** 지형 조작 도구.

> ⚠ **팀 확정 필요 항목.** 어느 쪽으로 정하든 이 한 줄만 바꾸면 전 스테이지가 따라온다.
> 도형님 의견을 먼저 듣고 싶은 부분이고, 기획서 1-5 를 고칠지 가이드 V1 을 고칠지 정해야 한다.

### 아직 남은 한계 (정직하게 기록)

E 회수를 **필수**로 만드는 퍼즐(예: "내가 칠한 발판 위에 서서 E 를 눌러 아래로 떨어진다")은
설계상 **소프트락 위험**과 붙어 다닌다. 레벨디자인 가이드 §2 "소프트락 금지 3규칙"을 지키려면
회수 순서를 틀렸을 때 탈출로가 항상 있어야 하는데, 그러면 회수를 안 해도 클리어할 수 있게 된다.
→ **이번 챕터에서는 E 를 "선택적이지만 가장 빠른 도구"로 배치**했다(스테이지 3 에서 소개).
E 필수 퍼즐은 체크포인트 재시작 버튼(일시정지 메뉴, P-B 요청 항목)이 들어온 뒤에 넣는 게 안전하다.

## 4. 물감 흐름 (Paint Drip) — "벽에 색칠하면 아래로 흐르는 연출"

`scripts/proto/paint_drip.gd` 신규.

**파티클이 아니라 `_draw()` 폴리곤으로 만든 이유**
- 파티클은 "점이 떨어지는" 건 잘하지만, 물감 특유의 **가늘고 길게 이어진 자국**
  (윗부분은 얇고 방울 머리만 두꺼운 형태)을 못 만든다.
- 자국이 남아야 하므로 수명이 길다 → 파티클이면 수백 개가 계속 살아있게 된다.
- `_draw()` 폴리곤 하나면 **노드 1개 · 드로우콜 1회**로 끝난다.

**수명 3단계**
1. **흐름** — 중력으로 길이가 늘어난다. 점성 때문에 등가속이 아니라 감속한다.
2. **굳음** — 멈춘 채로 젖은 광택이 서서히 사라진다.
3. **소멸** — 알파가 빠지며 사라진다 (자국 무한 누적 방지).

**언제 생기나** (`paint_fx.gd`)
| 맞은 면 | 확률 | 시작 위치 |
|---|---|---|
| 벽(세로면) | 85% | 맞은 그 높이에서 바로 |
| 아랫면 | 70% | 맞은 자리 |
| 윗면 | 25% | 플랫폼 아래 모서리로 넘쳐서 |

동시 존재 상한 40개 (성능 안전장치). 아트 에셋 의존 0.

## 6. 스테이지 1~5 — 하나의 완결된 챕터

`tools/build_stages.gd` 로 생성. **생성된 `.tscn` 은 직접 편집하지 말 것**(재실행 시 덮어써짐).

### 6-1. 레벨 디자인 수치 근거 (player.gd 실제 상수에서 계산)

```
move_speed 390 / jump_velocity -600 / gravity 1200 / 낙하중력배수 2.4

최대 상승   = 600² / (2×1200) = 150px ≈ 4.6칸
체공 시간   = 0.5s(상승) + 0.32s(하강) = 0.82s
최대 도약   = 390 × 0.82 ≈ 320px ≈ 10칸

→ 안전 설계값: 간격 ≤ 6칸(192px), 단차 ≤ 3칸(96px)
  (최대치의 60% 이하 = 상업 플랫포머의 통상 여유. 실수해도 다시 시도할 수 있다)
```

이 값은 `tools/test_stages.gd` 가 **BFS 그래프 시뮬레이션으로 자동 검사**한다.

### 6-2. 챕터 구성 (기승전결 — 레벨디자인 가이드 §1-2)

| 스테이지 | 리듬 | 새로 배우는 것 | 안전장치 |
|---|---|---|---|
| **1 첫 붓질** | 기 | 쏘면 발판이 생긴다 | 아래 전체가 **회색 안전바닥** — 떨어져도 안 죽음 |
| **2 색이 나를 죽인다** | 승 | 반대색 즉사 · Shift 전환 · **안전 전환 지대**(회색 발판) · 색문 | 회색 안전바닥 유지 |
| **3 되돌리기** | 승 | 계단식 상승 · **회색 함정 첫 등장**(V4) · E 회수 소개 | 회색 안전바닥 유지 |
| **4 회색의 대가** | 전 | **낙사 도입** · 회전톱(타이밍) · 움직이는 발판 · 회색 함정 밀도↑ | 체크포인트 2개 |
| **5 마지막 오르막** | 결 | 배운 것 전부 (색문 · 무너지는 발판 · 떨어지는 블록 · 톱 · 유령 사다리) | 체크포인트 2개 |

**설계 원칙 적용**
- "새 요소는 낙사 없는 안전한 구역에서 처음 등장" → 1~3 스테이지는 회색 안전바닥 위에서 진행
- "한 구역에 신규 부품은 1개만" → 스테이지당 새 장애물 1~2종
- "톱(타이밍)과 색칠(판단)을 동시에 요구하면 난이도가 곱셈으로 뛴다" → 4스테이지 이후에만 겹침
- **회색 함정(V4)** 은 3스테이지의 **안전한 곳**에서 처음 등장시켜, 실수로 회색을 만들어보게 유도

### 6-3. 시각 검증에서 실제로 고친 것 (스크린샷 → 수정 → 재확인)

| 발견 | 원인 | 조치 |
|---|---|---|
| 무색 발판이 **완전히 평평한 회색**, 무늬가 사라짐 | `mix(흑, 백, 0.5)` — 흑 벽돌(어두운 벽돌+밝은 줄눈)과 백 벽돌(밝은 벽돌+어두운 줄눈)이 정확히 반대라 평균 내면 무늬가 상쇄됨 | 무색 = **백 텍스처 × 0.55** (명암 유지, 명도만 절반) |
| 가로 1920px 바닥의 무늬가 **6배로 늘어나 뭉개짐** | 돌·흙·풀을 `tile_middle=false`(늘리기)로 둠 | **전 재질 `true`**(반복)로 통일 |
| 발판이 배경에 **묻힘** | 배경이 엔진 기본 회색(0.3)이라 무색 발판(0.5)과 명도가 겹침. 가이드 §5 는 45~55%를 회색 지형 전용으로 못박음 | 스테이지마다 **어두운 세로 그라데이션 배경**(0.07~0.20) 자동 생성 |
| 잉크가 **수염처럼 가늘게 갈라짐** | 32px 얇은 발판에 노이즈가 너무 잘고 셈 (0.20 / 5.0) | 0.13 / 3.2 로 완화 + 경계 부드러움 조정 |
| 5발 중 3발인데 **이미 다 칠해진 것처럼 보임** | 반지름 가속 지수 `pow(진행, 3.0)` 이 너무 빠름 | `pow(진행, 5.0)` — 마지막 한 발의 쾌감 확보 |
| 3칸짜리 얇은 회색 발판이 **얼룩처럼 뭉개짐** | 원본 테두리(50px)가 32px 발판 화면의 45%를 먹음 | ① 얇은 발판은 테두리를 비례 축소 ② 얇은 회색 전환대는 재질을 바위→벽돌로 교체 |
| 중앙 안내 문구가 **화면 왼쪽에 붙음** | 런타임에 붙인 Control 의 `size` 가 0 | 뷰포트 크기를 직접 읽고 글자 폭만큼 정확히 중앙 정렬 |
